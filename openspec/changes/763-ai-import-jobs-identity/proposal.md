# Proposal: AI-import jobs list identity — file name + imported episode, and no stale stage line (issue #763)

## Why

The AI-import jobs list (`AiImportJobsScreen` → `_JobRow`) is not identifiable
per row. Two defects feed each other:

1. **A stale stage line on every finished job (bug).** The extraction worker's
   last progress frame is `stage = storing_preview`, and `queue.mark_succeeded`
   never clears `progress` (only the *next* claim does). Every `succeeded` job
   therefore permanently carries `progress.stage == storing_preview`, and
   `_JobRow` renders the stage whenever `job.progress != null` — with no status
   guard. The result is a meaningless "Vorschau wird gespeichert …" that
   survives app restarts (the Drift cache persists the last row).
   The same block renders `aiJobEpisodesSeenLabel` ("Gefundene Episoden:") as a
   label with **no values** — it names the concept and never shows the episodes.
2. **No row identity (enhancement).** The row title is only `kind · date`
   (`Skript · 12. Okt. 2026`), so after a few imports the user cannot tell which
   document a row belongs to or which episode it produced. `AiImportJobRowView`
   carries `id`, `status`, `documentKind`, `createdAt`, `updatedAt`, `retries`,
   `lastError`, `progress`, `cost` — no file name, no imported episode. The
   backend has neither: uploads are a **raw body** with only a `Content-Type`,
   and the apply records nothing back onto the job (the response reports
   `created_episodes` as a count only). `source_handle` is an opaque storage
   handle and must never be repurposed as a display name.

## What Changes

- **Backend — terminal progress (belt and braces to the client guard).**
  `ai_import.ai_import_job.progress` is cleared on every terminal transition
  (`mark_succeeded`, `dead_letter` via `mark_failed`, `payload_unavailable`).
  The retryable `failed` branch keeps its progress (the job still has a future),
  and the claim-time reset stays as-is.
- **Backend — source file name.** The upload handlers accept an optional,
  percent-encoded UTF-8 `X-Document-Filename` header, decode it, sanitize it
  (basename only, no control characters, collapsed whitespace, length cap) and
  persist it as the additive `source_file_name` column on the job row. The raw
  body contract — and therefore every `415`/content-type path — is unchanged.
  A request without the header, and every pre-existing row, stays `NULL`: an
  honest absence, never a fabricated name.
- **Backend — imported episode(s).** A successful script apply persists the
  resolved target episodes with their per-episode applied row count as
  `applied_episodes` (additive, `serde(default)`) on the job. The data comes
  from the apply path itself (plan + targets, enriched at the API edge where
  the handler already resolves the target episode), never from a second
  projection lookup inside the write path. `ApplyAiImportResponse` returns the
  same list so the apply screen can name what it wrote.
  A schedule apply has no single target episode (it merges onto the project's
  existing scenes/days) and records none — the row degrades honestly.
- **Wire.** `AiImportJob.source_file_name` / `AiImportJob.applied_episodes` and
  `ApplyAiImportResponse.applied_episodes` land in `backend/openapi.yaml` (the
  `openapi_drift` artifact), the Dart client is regenerated by
  `scripts/regen-client.sh`, and the Drift jobs cache gains the columns with an
  additive migration.
- **Flutter — row rendering.** The stage/episode block renders only while the
  job is in progress (`jobStatusInProgress`), so no terminal row can ever show a
  stage. Running rows show the stage **and** the episode labels with values.
  The title becomes the file name (two lines max, ellipsized) with `kind · date`
  as secondary text; an unnamed row keeps today's `kind · date` title. The
  subtitle names the imported episode (`Skript · 299 Erlösung`, multi-episode
  `299 Erlösung (+2)`), and a succeeded applied job shows the outcome counts.

## Impact

- `backend/crates/core/src/ai/{views,ports,source_name}.rs`, `infra/src/ai/queue.rs`,
  `infra/src/ai/workers.rs`, `api/src/handlers/mod.rs`,
  migration `20261016000001_ai_import_job_identity`, `backend/openapi.yaml`,
  `frontend-flutter/vendor/breakdown_api/**`.
- `frontend-flutter/lib/data/cache/{ai_import_cache,cache_database,ai_import_jobs_cache_dao}.dart`,
  `lib/data/ai_import_repository.dart`,
  `lib/features/ai_import/import_jobs/{jobs_controller,jobs_screen,import_state,import_submit_screen}.dart`,
  `lib/l10n/app_{de,en}.arb`.
- No new env var, no new route, no new problem code. Every wire field is
  additive with a `serde(default)`, so an older client keeps deserializing.

## Delivery

Two stacked PRs (same OpenSpec change):

1. **Backend + wire + client regen** — migration, sanitizer, header, terminal
   progress reset, applied-episode persistence, `openapi.yaml`, vendored client.
2. **Flutter surface** — Drift migration, row view/mappers, screen rendering,
   ARB copy, widget/unit/golden tests.
