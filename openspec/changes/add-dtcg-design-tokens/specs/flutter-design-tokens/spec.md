## MODIFIED Requirements

### Requirement: Light and Dark M3 Themes from Tokens
`lib/design/theme.dart` SHALL define `AppThemes.light()` and
`AppThemes.dark()` via `ColorScheme` whose seed color and scheme roles
SHALL be sourced from the generated DTCG design tokens
(`frontend-flutter/lib/design/gen/`, regenerated by
`scripts/build-tokens.sh` from `design/tokens/**/*.json`), and `App`
SHALL pass both (`theme`, `darkTheme`) with
`themeMode: ThemeMode.system`. `lib/design/spacing.dart` SHALL expose
spacing values generated from the token source's dimension tokens.
Widgets SHALL use scheme roles and `lib/design` spacing tokens only —
no hardcoded `Color`, style, or spacing literals in widget code. Hand
edits to the generated `gen/` tree are forbidden (regenerate only).

#### Scenario: System switches to dark mode
- **WHEN** the device brightness setting changes to dark while the app
  is in the foreground.
- **THEN** the active screens and dialogs re-render in the dark scheme
  without an app restart.

#### Scenario: Hardcoded color in a new widget
- **WHEN** a review/CI check finds a `Color(...)` literal in a widget
  introduced by this change.
- **THEN** it is rejected; the color must come from `Theme.of(context)`
  color-scheme roles or `lib/design` tokens.

#### Scenario: Token source change flows into the theme
- **WHEN** a color token value in `design/tokens/` is changed and
  `scripts/build-tokens.sh` is run.
- **THEN** the regenerated `lib/design/gen/` reflects the new value and
  `AppThemes.light()`/`dark()` render the changed color without further
  code edits.

#### Scenario: CI token drift gate
- **WHEN** a CI run regenerates tokens into a throwaway tree and diffs
  it against the committed `lib/design/gen/` tree.
- **THEN** any difference fails the pipeline with a regenerate
  instruction.
