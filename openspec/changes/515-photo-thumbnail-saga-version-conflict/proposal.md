# 515 — photo_thumbnail_saga crash-loops on aggregate version conflict

## Why

The `PhotoThumbnailSaga` dispatches `NormalizeOriginal` + `GenerateVariant`
(Thumb/Medium) with a hardcoded `version: AggregateVersion::INITIAL` in each
command. The `Photo` aggregate's `Command::handle` enforces
`check_version(cmd.version)` — a strict equality check against the aggregate's
**current** version. Because the aggregate advances by one after every applied
event, the very first run already fails on the **second** dispatch
(`expected AggregateVersion(1), current AggregateVersion(2)`), and under the
supervisor's restart-and-replay of `PhotoUploaded` the aggregate is advanced
even further, producing a permanent crash-loop:

```
WARN ... restarting projector subscription after error projector.category="photo_thumbnail_saga"
  attempt=2 delay_ms=2336 error=version conflict: expected AggregateVersion(1), current AggregateVersion(2)
```

Net effect: `NormalizeOriginal` / `GenerateVariant` events are never durably
produced, so the costume read model shows `variants:[]` and the client gallery
stays on "processing" forever.

## Decision (user-confirmed in session)

**Option B — aggregate-level no-op idempotency** (the issue's literal
suggestion). `NormalizeOriginal` and `GenerateVariant` become **state-based,
aggregate-authoritative**, and version-tolerant:

- If the work is **already done** (original already `Ready` / variant already
  `Ready`), the command returns **no events** — a no-op — instead of failing
  with `VersionMismatch`/`ValidationError`.
- The emitted event version is always derived from the aggregate's own state
  (`self.version.next()`), accepting the version the aggregate is at, not the
  stale `cmd.version` carried by a saga replay.
- The strict `check_version(cmd.version)` guard is **dropped for these two
  saga-only commands only**. `MarkVariantFailed` / `DeletePhoto` keep strict
  versioning (the deletion saga still dispatches `DeletePhoto` with an exact
  expected version as a concurrency guard).

This converges under any redelivery pattern (partial, full, concurrent) because
the event-sourced aggregate is the single authority on whether the work exists,
and all dispatches for one photo serialize on the same `CommandService`
`EntityActor`. No write-side state read and no projection read is needed.

## Changes

1. **core** `crates/core/src/photo/aggregate.rs`
   - `Command<NormalizeOriginal>`: keep `check_not_deleted`; no-op (`Ok(vec![])`)
     when the Original variant is already `Ready`; drop `check_version`;
     emit `OriginalNormalized { version: self.version.next() }`.
   - `Command<GenerateVariant>`: keep `check_not_deleted`; no-op (`Ok(vec![])`)
     when the target variant is already `Ready` (replaces the current
     `ValidationError`); drop `check_version`; emit
     `VariantGenerated { version: self.version.next() }`.
   - Update the in-module mutation-test harness test
     `generate_variant_rejects_already_ready_variant` to assert the new no-op
     contract (kept paired with `generate_variant_succeeds_for_pending_variant`
     so the `==`/`!=` mutants stay killed), add
     `normalize_original_is_idempotent_when_already_ready`.
2. **core tests** `crates/core/tests/photo_aggregate.rs`
   - Replace `test_generate_variant_wrong_version` with a domain-level
     saga-redelivery regression: after the aggregate has advanced, a
     `GenerateVariant` carrying a **stale** `version` still succeeds (emits at
     `self.version.next()`), and re-dispatch of an already-ready variant is a
     no-op.
   - Add `test_generate_variant_idempotent_when_already_ready` and
     `test_normalize_original_idempotent_when_already_ready`.
3. **infra** `crates/infra/src/photo/sagas/thumbnail.rs`
   - Keep `ExpectedVersion::Any` + `AggregateVersion::INITIAL` fields but
     document that these are advisory for the idempotent saga commands.
   - Pass the **real generated byte sizes** into `GenerateVariant.size_bytes`
     (was hardcoded `0`), so the read model reports actual variant sizes.
4. **integration test** `crates/integration-tests/tests/photo_saga_redelivery.rs`
   (new, Tier 4, Postgres + SierraDB + Garage)
   - Upload a photo; drive a real `PhotoThumbnailSaga` via
     `EntityEventHandler::handle` **twice** with the same `PhotoUploaded` event
     (initial delivery + redelivery after the aggregate advanced to version 4).
   - Assert both deliveries succeed, the aggregate converges to version 4
     (no duplicate events on redelivery), the projection ends with real
     `content_type` + `size_bytes > 0`, and Thumb/Medium are `Ready` with
     non-zero sizes.

## Acceptance criteria (from issue)

- [ ] Saga dispatch is idempotent under redelivery: replaying `PhotoUploaded`
      after the aggregate advanced no longer raises a version conflict.
- [ ] The redelivery stabilizes and produces Thumb/Medium variants; no
      duplicate `VariantGenerated` events are appended.
- [ ] `projection_photo` ends with real `size_bytes` / `content_type` and the
      variant rows are `Ready`.
- [ ] Existing strict versioning for `DeletePhoto` / `MarkVariantFailed` is
      preserved.
