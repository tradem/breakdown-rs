# Proposal: localize the Flutter app via the official gen-l10n pipeline (issue #518, ADR-034)

## Why

The Flutter client has no internationalization or localization setup at
all: `pubspec.yaml` carries neither `flutter_localizations` nor `intl`,
there is no `l10n.yaml`, and user-facing strings are hardcoded inline in
widgets — in mixed languages (English error narratives like
`'A season with that number already exists.'` beside German dialog copy
like `'Staffel wirklich löschen?'`). Material-owned surfaces (date
pickers, tooltips, a11y labels) render in framework defaults regardless of
device locale, and the conventions that already *anticipate* a message
catalog (gitleaks scanning `.arb`, the localized 403 narrative, UI copy
per problem `code` localized client-side) have no mechanism to satisfy
them.

Issue #518 settles the architecture decision as **ADR-034**: adopt the
official Flutter i18n pipeline — `flutter_localizations` + `flutter
gen-l10n` (ARB) + `intl` — over `slang` (third-party, non-standard
format) and a Fluent port (runtime parsing, no compile-time/CI gate).
This change implements that decision.

## What Changes

- Author **ADR-034**
  (`backend/docs/architecture/adrs/ADR-034-flutter-app-localization-gen-l10n.md`,
  client-ADR precedent of ADR-032/033) recording the decision and the
  rejected alternatives (`slang`, `easy_localization`, Dart Fluent port).
- Add `flutter_localizations` (SDK) and `intl` to `frontend-flutter`,
  wire `localizationsDelegates`, `supportedLocales` (`de` template, `en`)
  and locale resolution into `MaterialApp.router`.
- Introduce the message catalog `frontend-flutter/lib/l10n/`
  (`app_de.arb` template, `app_en.arb`) generated by `flutter gen-l10n`
  into `AppLocalizations`, configured via `l10n.yaml` with
  `nullable-getter: false` and `untranslated-messages-file` wired to a
  CI gate that parses the JSON report and fails on any untranslated
  entry (a complete catalog writes `{}`, so a file-size check would
  false-positive), mirroring the OpenAPI drift gate.
- Migrate all user-facing copy in `lib/features/**` from hardcoded
  strings to catalog keys; copy keys are sourced from
  `docs/design/glossary.md` (German labels are the canonical shipped
  copy, quoted verbatim in the ARB template).
- Localize problem-`code` narratives (title/body/CTA per stable `code`,
  never interpolating backend `detail`) through catalog keys, replacing
  the ad-hoc hardcoded code→text maps (e.g. `seasons_screen.dart`).
- Use `intl` `DateFormat`/`NumberFormat` for all dates and numbers
  rendered on screens; remove hand-rolled format strings.
- Update widget tests and goldens for localized trees; add locale-aware
  test coverage for at least one screen in both locales.
- Extend `docs/design/glossary.md` workflow note: every new screen
  records its labels as ARB copy keys from day one — the glossary stays
  the index (copy key → usage context) while the ARB catalog stores the
  actual strings.

## Capabilities

### New Capabilities

- `flutter-app-localization`: official gen-l10n message catalog (de
  template, en), localization wiring, glossary-sourced copy keys,
  problem-code narratives, intl-based formats, and the CI
  untranslated-keys gate.

### Modified Capabilities

- None. (Existing flutter-* specs describe behavior, not copy storage;
  their requirements are unchanged by the message-catalog migration.)

## Impact

- **Code**: all feature screens under `frontend-flutter/lib/features/**`
  (string migration), `app.dart` (wiring), `pubspec.yaml`,
  new `frontend-flutter/lib/l10n/` + `l10n.yaml`.
- **ADR**: new ADR-034 in `backend/docs/architecture/adrs/` (document
  only; no backend behavior change).
- **CI**: `flutter gen-l10n` + untranslated-messages gate in the
  frontend workflow; gitleaks already scans `.arb`.
- **Docs**: `docs/design/glossary.md` (copy-key ↔ ARB-key alignment
  note).
- **No wire-contract change**: backend `openapi.yaml` untouched; the
  client keeps branching on stable problem `code` per RFC 9457 /
  ADR-031.

## Non-goals

- Additional locales beyond `de` and `en` (add when a store listing
  demands it).
- Full RTL mirroring audit beyond framework defaults and logical
  properties.
- Localizing backend-generated PDF reports (server-side concern).
- Sharing Fluent `.ftl` message files between backend and client —
  architecturally rejected (client must not render backend `detail`;
  see ADR-031 client contract).
- Pseudo-locale tooling.
