## Problem

The weekly mutation-testing CI run [30189219445](https://github.com/tradem/breakdown-rs/actions/runs/30189219445)
detected 125 surviving mutants. Most were fixed in `fix/mutation-testing-survivors-weekly-30189219445`,
but **6 mutants in `crates/api/src/auth/jwks.rs`** remain uncatchable by unit tests in the current test
harness:

### Location 1: Cache TTL comparison (line 100)

`CachingJwksProvider::decoding_keys` checks whether the cached JWKS is still fresh via
`cached.fetched_at.elapsed() < self.ttl`. The `<` operator has 3 surviving variants (`==`, `>`, `<=`):

```
MISSED  crates/api/src/auth/jwks.rs:100:48 — replace < with ==
MISSED  crates/api/src/auth/jwks.rs:100:48 — replace < with >
MISSED  crates/api/src/auth/jwks.rs:100:48 — replace < with <=
```

These survive because `Instant::elapsed()` cannot be advanced in unit tests without time-manipulation
infrastructure (`tokio::time::pause()` only affects async sleep, not `Instant`).

### Location 2: JWK filtering logic (line 123)

The key-filtering predicate `if jwk.kty != "RSA" || jwk.use_.as_deref() == Some("enc")` has 3 surviving
operator variants:

```
MISSED  crates/api/src/auth/jwks.rs:123:24 — replace != with ==
MISSED  crates/api/src/auth/jwks.rs:123:33 — replace || with &&
MISSED  crates/api/src/auth/jwks.rs:123:56 — replace == with !=
```

To catch these a test must serve a JWKS with realistically formatted RSA keys over HTTP, then call
`decoding_keys()`. The `jsonwebtoken::DecodingKey::from_rsa_components` function rejects RSA keys
generated by the `rsa` crate in dev-dependencies under certain conditions, making a straightforward
inline test non-trivial.

## Proposed solution

Two approaches are viable:

### Approach A — Local HTTP test server

Start a local Axum server in the test that serves a JWKS endpoint with:
- One valid RSA signing key with a `kid`
- One encryption-purpose key (`"use": "enc"`)
- One non-RSA key (`"kty": "EC"`)
- One RSA key without a `kid`

Then verify `decoding_keys()` returns exactly 1 key (the valid signing key). This exercises the
`||`/`&&`, `!=`/`==` operators.

### Approach B — Timed cache test

Use `tokio::time::pause()` + a shortened TTL to force cache expiry between two calls, verifying the
second call re-fetches from the server. This exercises the `<`/`==`/`>`/`<=` operators.

Both approaches require `tokio` time-manipulation features and a controlled HTTP endpoint.

## Systematic implementation plan

1. **Make cache time controllable in tests without changing production behavior.**
   Use Tokio's monotonic `time::Instant` for the cache timestamp; in production it
   remains monotonic, while the test runtime can pause and advance it deterministically.
2. **Build one realistic JWKS fixture.**
   Generate a valid RSA public key and serve it from a local Axum endpoint together
   with an encryption-purpose RSA key, a non-RSA key, and an RSA key without a `kid`.
3. **Verify the key-filtering contract.**
   Assert that `decoding_keys()` returns exactly the one RSA signing key with a `kid`.
   This distinguishes each `!=`/`||`/`==` mutation from the intended predicate.
4. **Verify all cache comparison boundaries.**
   With Tokio time paused, call the provider at the initial instant, exactly at the
   TTL, and after the TTL. Assert that the endpoint is called once, twice, and three
   times respectively. This covers fresh-cache reuse, strict expiry, and post-expiry
   refresh, including all three comparison mutants.
5. **Run focused tests and formatting, then run the API mutation target.**
   The focused test must pass before mutation testing; the final acceptance check is
   zero missed `jwks.rs` mutants in the `mutate-security` scope.
