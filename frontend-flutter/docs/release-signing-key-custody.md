# Android Release Signing Key — Custody Procedure

> Scope: the single project-owned Android release keystore (Decision **D9**,
> OpenSpec change `add-android-release-workflow`, spec
> `flutter-release-signing`). Every binary the project itself publishes —
> GitHub Release APKs/AABs now, developer-signed F-Droid artifacts later —
> is signed with this one key. F-Droid *source builds* (F-Droid's buildbot
> key) and Google Play binaries (Play App Signing's key) are **outside** this
> guarantee.

The signing key is the project's distribution trust anchor: **losing it is
unrecoverable** for all already-published channels (no key rotation possible
without forcing every tester to uninstall/reinstall). Treat it like a root
CA key, not like a build credential.

## 1. Generation (once, offline)

Run ONCE on an air-gapped or fully trusted offline machine — never on a CI
runner, never inside the repository checkout:

```bash
keytool -genkeypair -v \
  -keystore breakdown-release.jks \
  -alias <ALIAS> \
  -keyalg RSA -keysize 4096 -validity 10950 \
  -storepass <STOREPASS> -keypass <KEYPASS> \
  -dname "CN=Breakdown RS, OU=Breakdown RS, O=Breakdown RS, L=<city>, C=DE"
```

- `<STOREPASS>` / `<KEYPASS>`: generated by a password manager (≥ 32 random
  chars); they live ONLY in the password manager and the CI environment
  secret — never in the repo, never in a shell history, never in this doc.
- `<ALIAS>`: short lowercase identifier, e.g. the release year.
- Validity: 30 years (`-validity 10950`) — Android requires the certificate
  to outlive every binary it signed.

Then record the certificate fingerprint (needed later for
`AllowedAPKSigningKeys` in the `add-fdroid-inclusion` change):

```bash
keytool -list -v -keystore breakdown-release.jks -alias <ALIAS> \
  | grep "SHA-256:"
```

## 2. Fingerprint constant

> ✅ **Recorded at bootstrap (task 1.2).** The fingerprint below is the
> recorded project signing-certificate fingerprint, lowercase and
> colon-free (the format F-Droid's `AllowedAPKSigningKeys` expects). It
> is mirrored verbatim in `.github/workflows/flutter-release.yml`
> (build job `env:`). If it ever changes (key rotation, §6), both places
> must be updated together.

```
EXPECTED_SHA256_FINGERPRINT=bfd0184e1de57e33669f8ec19c3b3c1b111332fa4424f1b999b2740bd89fbc8b
```

Offline backups (§4) and the four `release`-environment secrets are
maintainer-side; verify the backup fingerprint against this value after
every re-import.

The same value must be set as the `EXPECTED_SHA256_FINGERPRINT` env value in
`.github/workflows/flutter-release.yml` (build job `env:`) — the release
workflow refuses to publish while it is unset (`TBD`), so an unbootstrapped
pipeline cannot produce an unverifiable artifact. After bootstrap, a signed
APK must verify against this exact fingerprint:

```bash
apksigner verify --print-certs breakdown-<version>-arm64-v8a.apk
# Signer #1 certificate SHA-256 digest: <the recorded fingerprint, colons>
```

## 3. CI secrets

Base64-encode the keystore and store it as environment-scoped GitHub Actions
secrets (scoped to the protected `release` environment — see task 1.4 and
`flutter-release.yml`; NOT as plain repository secrets):

| Secret | Value |
|---|---|
| `KEYSTORE_BASE64` | `base64 -w0 breakdown-release.jks` output |
| `KEYSTORE_PASSWORD` | keystore (store) passphrase |
| `KEY_ALIAS` | the key alias |
| `KEY_PASSWORD` | the key passphrase |

The workflow decodes `KEYSTORE_BASE64` into `$RUNNER_TEMP` at build time and
never echoes any of the four values. The keystore file itself is gitignored
(`*.jks`, `*.keystore`) and covered by gitleaks rules (root
`.gitleaks.toml`, `frontend-flutter/.gitleaks.toml`).

## 4. Offline backup — two maintainers

At least **two maintainers** each hold a full offline copy of:

- `breakdown-release.jks`,
- the store/key passphrases and alias (in the shared password manager, plus
  a printed emergency copy in each maintainer's separate safe storage),

stored on encrypted removable media, geographically separated. Verify each
backup by re-importing it into a throwaway keystore tool and comparing the
SHA-256 fingerprint from §2. Repeat the verification after every rotation.

Custodians (recorded in the change's design.md "Open Questions"):
**tradem** and **imac.ric@gmail.com**. This must be resolved before task
1.2 is executed.

## 5. Regenerating CI secrets from a backup

A new maintainer recovers capability without regenerating the key:

1. Obtain the offline backup from one of the two custodians (§4).
2. Verify the fingerprint equals §2 (`keytool -list`).
3. Re-encode: `base64 -w0 breakdown-release.jks`.
4. Update the four environment secrets on the `release` environment.

Never generate a NEW keystore for this purpose — that would be a key
rotation (§6), not a recovery.

## 6. Key rotation (break-glass only)

Android signature trust makes routine rotation impossible: a binary signed
with a new key cannot update a binary signed with the old one. Rotation is
therefore only a break-glass procedure when the key material or a passphrase
is suspected compromised:

1. Follow §1 to generate a fresh keystore; update §2's fingerprint.
2. Publish a transition release under the OLD key (if still usable)
   announcing the migration; all channels move to the new key together.
3. Testers must uninstall/reinstall once; announce this loudly.
4. Update this doc, the workflow fingerprint gate, and (later)
   `AllowedAPKSigningKeys` in `add-fdroid-inclusion`.

### 6.1 Planned migration path — APK Signature Scheme v3 key rotation

The §6 uninstall/reinstall pain applies only to APKs without a rotation
lineage. **APK Signature Scheme v3** carries a **Proof-of-Rotation
lineage**: the APK embeds the chain of past signing certificates, so
Android accepts an update signed with a NEW certificate as long as it is
linked back to the original one in the lineage. That turns rotation from
break-glass into a normal, planned migration.

Toolchain reality (verified locally during the
`add-android-release-workflow` session):

- AGP/apksigner do NOT enable v3 by default when `minSdkVersion < 28` —
  the first signing-config draft produced v2-only APKs (verified:
  `apksigner verify --verbose` → `v2: true, v3: false`).
- The release signingConfig therefore sets **`enableV3Signing = true`**
  explicitly (`frontend-flutter/android/app/build.gradle.kts`), after
  which release APKs verify with BOTH v2 and v3 (verified:
  `v2: true, v3: true`). v2 keeps the APK installable on older devices;
  v3 establishes the lineage root.
- The first v3-signed release implicitly enrolls the project certificate
  as the lineage root — no extra tooling needed for the initial state.

Why we care: algorithm migration, not key loss. The 30-year validity
(§1) covers the certificates of every published binary, but the
*algorithm* (RSA-4096 today) will not stay the right choice for 30 years.
Once post-quantum signing (e.g. ML-DSA) is supported by Android's APK
packaging toolchain (`apksigner`/AGP packaging does NOT support it
yet — as of build-tools 37 / AGP 9), the planned path is:

1. Generate the successor keystore with the post-quantum algorithm; update
   §2's fingerprint and the workflow gate.
2. Sign the transition release with the OLD key plus a rotation lineage
   file pointing at the NEW certificate (apksigner
   `--rotation-min-sdk`/lineage input; the Gradle signingConfig grows a
   lineage option then).
3. Every later release is signed by the NEW key and installs over existing
   installs WITHOUT uninstall (Android walks the lineage back to the root).
4. Update `AllowedAPKSigningKeys` in `add-fdroid-inclusion` to the new
   fingerprint — fdroiddata verification does not walk lineages, so the
   metadata MR must pin the NEW fingerprint.
5. Record the rotation event in this doc (§2 gains a lineage list of
   past/current fingerprints and their validity ranges).

Note on the pre-quantum threat model: signature FORGERY is not subject to
"harvest now, decrypt later" — a forged update must carry a valid
signature at install time, so a future quantum computer does not
retroactively compromise already-published APKs. The migration pressure
is therefore a planned, calm one: keep RSA-4096 until Android packaging
supports a post-quantum scheme, then rotate via v3 lineage. Review of
this doc's §2/§6.1 whenever NIST/Google move the deprecation timelines
(IR 8547: RSA-2048/ECDSA-256 deprecated ~2030–2031) is a maintainer task,
not a CI gate.

Verification recipe (rerun any time):

```bash
apksigner verify --verbose breakdown-<version>-arm64-v8a.apk
# Expect: "Verified using v2 scheme ...: true"
#         "Verified using v3 scheme ...: true"   <- lineage root enrolled
```

## 7. Cross-channel invariant (D9)

- GitHub Release APKs/AABs and later developer-signed F-Droid binaries
  (fdroiddata `Binaries:`) carry exactly this fingerprint — a follow-up
  build with the same key updates in place, no uninstall.
- F-Droid *source builds* are signed by F-Droid's buildbot key — no
  cross-channel fingerprint claim is made for them.
- Play-distributed binaries are re-keyed by Play App Signing — the
  enrollment model is decided in `add-play-store-release`.
